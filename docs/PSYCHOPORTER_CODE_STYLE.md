# Psychoporter Code Style
## Когнитивно-эргономический профиль Ivan-VHS Code Style

**Версия:** 1.0  
**Статус:** нормативное дополнение к Ivan-VHS Code Style  
**Дата:** 2026-11-25  
**Область:** Reaper, DuckOS и связанные репозитории Ivan-VHS

> Думать широко. Называть точно. Читать линейно. Менять узко. Проверять полностью.

## 1. Назначение и границы

Психопортер — авторская методология проектирования кода для человека, который будет его читать, отлаживать и сопровождать. Она переносит внимание с «красивой строки» на понятный ход мысли: имя задаёт контекст, структура показывает последовательность, границы модуля объясняют ответственность, а тест фиксирует ожидаемое поведение.

Психопортер — инженерная метафора и набор проверяемых эвристик. Он **не является психологическим тестом, диагнозом или утверждением о нейробиологии**. Утверждения о фиксированной ёмкости рабочей памяти, обязательном количестве слогов, «активации моторной коры» или универсальном эмоциональном эффекте слов не используются как технические доказательства.

Стандарт подчиняется более высоким требованиям: корректности, безопасности, ABI, производительности, языковым идиомам, доступности и доказуемости поведения. Понятность не оправдывает эвфемизм, потерю точности или скрытие опасной операции.

## 2. Базовый характер кода

Код должен выражать **собранную ясность**:

- естественный для своего языка, без искусственной литературности;
- конкретный в именах и контрактах;
- последовательный в терминах внутри всего проекта;
- линейный там, где последовательность операций важна;
- краткий там, где контекст уже очевиден;
- подробный там, где скрытая цена, инвариант или риск требуют объяснения;
- честный о состоянии реализации и границах гарантий.

Психопортер дополняет [Ivan-VHS Code Style](https://github.com/Ivan-VHS/Reaper/blob/main/docs/IVAN_VHS_CODE_STYLE.md), а не создаёт конкурирующие правила форматирования или новый язык программирования. Для Reaper этот общий профиль конкретизируется языковым [Кодексом Psychoporter 666](https://github.com/Ivan-VHS/Reaper/blob/main/docs/PSYCHOPORTER_666.md), который отдельно фиксирует текущую грамматику, целевые возможности и host/platform boundaries.

## 3. Именование: точность без многословия

Имя должно сокращать работу по восстановлению контекста. Выбирай самое короткое имя, которое остаётся однозначным в текущей области видимости.

### 3.1. Предпочтения

- Используй термин предметной области вместо универсальных `data`, `object`, `value`, `temp`, если реальная роль известна.
- Для функции называй действие и его объект: `validate_region`, `release_frame`, `resolve_symbol`.
- Для состояния используй ясные булевы формы: `is_ready`, `has_mapping`, `can_retry`.
- Различай получение, изменение и уничтожение ресурса: `read_register`, `update_mapping`, `terminate_process`.
- Сохраняй один термин для одного понятия на границах модулей и репозиториев.
- Используй короткие имена для индексов и локальных переменных, когда область видимости действительно мала: `i`, `offset`, `len`, `src`, `dst` — нормальны в очевидном цикле или низкоуровневой операции.
- Уважай существующие публичные имена и ABI. Переименование публичного символа — изменение контракта, а не косметика.

### 3.2. Чего избегать

- Не раздувай имя до предложения: `fetch_user_preferences_from_cache_and_validate_them` обычно хуже, чем `load_preferences` с чётким контрактом.
- Не скрывай смысл за внутренними аббревиатурами, которые не определены в проектном словаре.
- Не называй функцию только по её реализации, если это привязывает API к случайной детали.
- Не маскируй реальное действие приятным словом. `terminate_process` нельзя заменить на `close_session_gracefully`, если процесс действительно принудительно завершается.
- Не переименовывай `kill`, `destroy`, `panic` или `error` автоматически: термин должен соответствовать фактической семантике и принятому словарю подсистемы.

### 3.3. Принцип контекста

Внутри модуля допустимо `region`; на внешнем API может понадобиться `memory_region`. Не дублируй имя модуля в каждом символе, если импорт и область видимости уже дают контекст. И наоборот, не делай локальное имя абстрактным, если оно пересекает несколько подсистем.

## 4. Поток чтения: одна мысль за раз

Читатель должен видеть последовательность: входные условия → проверка → основное действие → результат.

- Проверяй внешние данные на границе, до опасного использования.
- Используй guard clauses и ранний возврат, когда они убирают лишнюю вложенность.
- Держи основной путь исполнения видимым, но не прячь ошибки ради «happy path first».
- Сохраняй проверки рядом с защищаемым доступом к памяти, индексом или регистром.
- Не выноси короткое выражение в функцию только ради уменьшения числа строк.
- Выноси блок, если у него есть собственная ответственность, повторное использование или важный инвариант, который становится проще проверить отдельно.
- Избегай скрытых переходов управления, неочевидных глобальных состояний и неявных побочных эффектов.

### 4.1. Вложенность — сигнал, не закон

Глубокая вложенность затрудняет чтение, но фиксированный предел «три уровня» не подходит для всех языков и задач. При нескольких уровнях вложенности проверь, можно ли выделить намерение, инвертировать условие или разделить ответственность. Не ломай естественную структуру алгоритма ради формального лимита.

### 4.2. Декларативность без сокрытия цены

Декларативная форма хороша, если она делает намерение яснее. Не применяй map/filter/цепочки автоматически, когда цикл лучше показывает владение памятью, порядок операций, ранний выход, синхронизацию или стоимость аллокаций.

## 5. Визуальная ритмика и форматирование

- Один логический шаг — одна понятная строка или компактный блок.
- Пустая строка разделяет смену мысли, а не каждый оператор.
- Скобки и отступы должны показывать реальные границы блока.
- Не выравнивай присваивания пробелами вручную в длинные колонки: это создаёт шум в diff и конфликтует с форматтерами.
- Следуй formatter/linter проекта. Не добавляй отдельные эстетические правила поверх автоматического форматирования без практической причины.
- Не дроби короткие и очевидные конструкции до потери цельности.
- Не сжимай несколько операций в одну строку ради компактности.

## 6. Архитектура: карта ответственности

- Группируй код по функции продукта или доменной ответственности, когда это помогает удержать связанный сценарий рядом.
- Сохраняй слои там, где они защищают границы: kernel/driver, ABI, runtime, application, UI, storage.
- Направляй зависимости к стабильным контрактам; не позволяй UI, файловой системе или конкретному устройству становиться скрытой зависимостью доменной логики.
- Предпочитай вертикальный срез: одна функция, проходящая через контракт, реализацию, тест и документацию, лучше нескольких незавершённых подсистем.
- Не создавай абстракцию ради единственного вызова без вариативности или реальной границы.
- Не объединяй независимые подсистемы только ради визуальной компактности репозитория.
- Каждый модуль должен иметь понятное владение состоянием, ресурсами и ошибками.

## 7. Ошибки и восстановление

Ошибка — полноценный исход операции, а не повод скрывать состояние.

- Используй типизированный результат/код ошибки там, где это поддерживает язык и API.
- Разделяй ошибку входных данных, отказ доступа, нехватку ресурса, несовместимость версии и отказ устройства.
- Сообщение должно называть действие, объект и причину; recovery hint добавляй только если он достоверен.
- Не проглатывай ошибку и не продолжай с фиктивным значением.
- Graceful degradation допустима, если безопасная семантика сохраняется; при отказе проверки подписи или capability нельзя «мягко» продолжать привилегированную операцию.
- Стабильные машинные коды ошибок не переиспользуй с новым смыслом.
- Не помещай секреты, токены, полные частные данные или чувствительные адреса в логи.

## 8. Комментарии и история решений

Комментарии добавляют сведения, которых нет в коде:

- почему нужен необычный порядок операций;
- какой аппаратный, ABI или протокольный инвариант защищается;
- почему выбран конкретный алгоритм;
- какие ограничения внешнего стандарта нельзя нарушать;
- где проходит граница доверия или владения.

Не пересказывай очевидное действие. Удаляй устаревший комментарий, если он противоречит реализации. Для долгоживущих архитектурных решений используй ADR или отдельную спецификацию. TODO должен ссылаться на реальную задачу или содержать конкретный проверяемый следующий шаг; не встраивай календарные обещания в исходник.

## 9. Тесты как проверка намерения

Название теста описывает условие и ожидаемое поведение. Структура Arrange–Act–Assert полезна, но не обязательна, если тест проще и понятнее в другом виде.

Покрывай:
- нормальный сценарий;
- неверные данные и отказ;
- нулевые, граничные и переполняющиеся значения;
- отсутствие capability и нарушение границы доверия;
- регрессию, которую исправляет изменение;
- конкурентность, повторяемость и отказ адаптера, если это относится к контракту.

Проверяй публичный результат и инвариант, а не внутреннее расположение строк. Для системного кода добавляй negative tests, host-side fake adapters, fuzz/property tests и QEMU/hardware-in-the-loop только там, где соответствующая инфраструктура действительно существует.

## 10. Рефакторинг: малые законченные изменения

- Перед изменением прочитай владельца функции, потребителей, тесты и контракт.
- Сначала зафиксируй наблюдаемое поведение.
- Меняй одну связную ответственность за раз.
- После каждого смыслового шага запускай минимальный относящийся к нему набор проверок.
- Не смешивай переименование, форматирование, изменение поведения и миграцию ABI в один неразличимый diff.
- Не переписывай уже ясный код только для демонстрации стиля.
- Удаляй мёртвый код лишь после проверки ссылок, сборки и совместимости.
- В PR указывай точные команды и результаты. Непройденная или не запущенная проверка так и обозначается.

## 11. Профили языка и платформы

Психопортер не подменяет синтаксис, ABI или конвенции языка.

### Reaper

- Используй фактический синтаксис Reaper и его настоящие операторы; основной оператор композиции — `::`.
- Не вставляй Rust-, C- или Python-подобный псевдосинтаксис в примеры, выдаваемые за компилируемый Reaper.
- Держи типизацию, владение, эффекты и аппаратные возможности явными по мере того, как соответствующие функции языка действительно реализованы.
- Не объявляй freestanding, inline assembly, `unsafe`, native ELF backend или MMIO готовыми возможностями без компилятора, реализации и тестов.
- Python reference runtime остаётся совместимостной реализацией; он не является заменой будущему Reaper-native backend.

Канонический небольшой пример текущего синтаксиса:

~~~reaper
craft double(value) {
    yield value * 2
}

make total := [1, 2, 3] :: map(double) :: sum()
emit "total = " ++ text(total)
~~~

### DuckOS и системный C

- Reaper — целевое направление системной логики DuckOS.
- C11/x86_64 допустим как узкий проверяемый platform/boot bridge, пока Reaper не имеет нужного native target и ABI.
- Для памяти, MMIO, DMA, IRQ и загрузки указывай ширину, выравнивание, границы, владение и условия отказа.
- Короткие имена регистров, полей ABI и локальных индексов допустимы, когда они следуют спецификации; не переименовывай стандартные аппаратные термины в литературные эквиваленты.
- Не помещай произвольный доступ к физической памяти или привилегированные инструкции в обычную прикладную библиотеку.

### Другие проекты

Сохраняй C11, C17, C++20, Rust, JavaScript, Python и другие нативные стеки владельца репозитория. Единым должен быть уровень ясности и инженерной дисциплины, а не синтаксис.

## 12. Ревью и проверка полезности

Ревьюер спрашивает: «Какое намерение здесь выражено?», «Какая гарантия сохраняется?», «Можно ли понять отказ без изучения всей системы?». Комментарии должны быть уважительными, конкретными и привязанными к поведению.

Когнитивная эргономика проверяется практично: может ли новый сопровождающий найти вход, проследить основной поток, понять владение ресурсом, назвать отказ и определить нужный тест без скрытых знаний автора? При необходимости это проверяют задачей чтения кода и наблюдаемым временем/ошибками, а не предположениями о мозге.

## 13. Краткий чек-лист

Перед merge:

- [ ] Имена отражают роль и точную семантику.
- [ ] Основной поток и точки отказа видны.
- [ ] Вложенность и абстракции оправданы.
- [ ] Форматирование соответствует formatter проекта.
- [ ] Контракты, владение, эффекты и пределы указаны.
- [ ] Ошибки не скрываются; привилегированные действия fail closed.
- [ ] Комментарии объясняют причины и инварианты.
- [ ] Тесты проверяют поведение и граничные случаи.
- [ ] Diff ограничен одной связной задачей.
- [ ] Документация и заявления о зрелости подтверждены реализацией.

**Правило финального выбора:** если решение не улучшает корректность, безопасность, ясность сопровождения или измеренную производительность — не добавляй его.
