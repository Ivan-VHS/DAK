# DAKOS — инженерный профиль и критерии реализации

**Проект:** Ivan-VHS/DAKOS  
**Автор архитектурного направления:** Ivan-VHS  
**Статус:** план и acceptance contract. Ни одна подсистема не считается готовой только по наличию этого документа.

## Системная идентичность

DAKOS должна быть не коллекцией несвязанных программ, а собственной вычислительной средой. Цельность возникает из стабильных контрактов между boot chain, kernel, драйверами, процессами, службами, графикой, пакетами и инструментами разработки.

## Принципы, переведённые в системную архитектуру

### Самостоятельность без переписывания всего сразу
Собственная реализация важна там, где она создаёт контроль над ABI, безопасностью или моделью продукта. Но повторно использовать открытые стандарты, спецификации, форматы и проверенные инструменты допустимо при соблюдении лицензий. Независимость — это контроль над реализацией, а не отказ от совместимости.

### Один контракт на каждую границу
Для каждой подсистемы заранее определить: входные данные, выход, владение памятью, синхронизацию, права, ошибки, версии и поведение при отказе. Не позволять приложению зависеть от внутренней структуры ядра.

### Безопасность как базовая модель
Права выдаются явно. Процесс получает минимальные capabilities. Драйверы и системные службы изолируются настолько, насколько позволяет текущая архитектура. Все внешние данные считаются недоверенными. Package manager проверяет происхождение и целостность до изменения установленной системы.

### Объяснимая система
Загрузка, запуск службы, отказ драйвера и ошибка пакета должны оставлять диагностическое событие с компонентом, кодом причины, фазой и доступным контекстом. Логи не должны содержать секреты и содержимое пользовательских файлов по умолчанию.

### Читаемый системный код
Небольшие функции, явные типы, ясное владение памятью, проверка размеров до чтения/записи, единая модель ошибок. Не строить обобщённую инфраструктуру прежде, чем появится минимум два реальных потребителя.

## Рекомендуемые логические уровни

1. **Boot:** загрузочная конфигурация, передача карты памяти и аргументов ядру, сериализованный boot log.
2. **Kernel core:** архитектурно-зависимый слой, обработка исключений/прерываний, физическая и виртуальная память, таймер, планировщик и базовые примитивы синхронизации.
3. **Kernel services:** VFS, IPC, процессы, дескрипторы и системные вызовы.
4. **Initramfs и userland:** первый процесс, библиотека системного ABI, менеджер служб и диагностические утилиты.
5. **Device model:** перечисление устройств, драйверный ABI, буферы DMA и жизненный цикл драйвера.
6. **Graphics:** framebuffer backend, дисплейная композиция, оконная модель, input routing, затем отдельный GPU backend.
7. **System distribution:** package manager, подписанные репозитории, транзакционное обновление, recovery и установка.
8. **Application isolation:** sandbox, capabilities, профили ресурсов и явный доступ к файлам/устройствам.

Порядок слоёв задаёт зависимости, но не требует преждевременно реализовывать весь список.

## Обязательные архитектурные решения (ADR)

До соответствующей реализации публиковать короткое решение с контекстом, вариантами, выбором, последствиями и планом миграции:

- первичная архитектура процессора и формат загрузки;
- модель ядра и границы драйверов;
- схема виртуальной памяти и адресное пространство;
- формат системных вызовов и ABI;
- модель IPC и событий;
- формат файловой системы и VFS;
- модель графики и GPU backend;
- подпись пакетов и rollback;
- язык bootstrap и этапы перехода на Reaper.

Не выбирать ABI только по удобству текущего компилятора. Он должен оставаться стабильным, версионируемым и проверяемым.

## Связь с Reaper

Reaper может стать основным языком DAKOS только поэтапно:

1. реализовать и тестировать стабильную семантику языка;
2. получить native code generation для выбранной архитектуры;
3. определить calling convention, ownership, error ABI и системные вызовы;
4. пройти ABI conformance suite на тестовом userland;
5. собрать независимую маленькую системную утилиту;
6. после этого расширять долю системных компонентов на Reaper.

До прохождения этих пунктов bootstrap не должен зависеть от неподтверждённых возможностей Reaper.

## Вертикальные срезы

### Slice 0 — воспроизводимый bootstrap
Сборка образа с фиксированными версиями инструментов, запуск в эмуляторе, передача управления минимальному ядру, диагностическая строка и код завершения. CI сохраняет лог и checksum образа.

### Slice 1 — память и аварийный путь
Проверка карты памяти, простой allocator, обнаружение некорректного диапазона, panic path с кодом причины. Негативные тесты на обрезанные структуры и переполнение.

### Slice 2 — первый процесс
Initramfs, первый user process, минимальная системная библиотека и один read-only системный вызов. Проверка отказа при неверном ABI.

### Slice 3 — службы и файловая система
VFS с ограниченным набором операций, IPC request/reply, запуск/остановка одной службы, журнал событий.

### Slice 4 — графический путь
Сначала framebuffer и input; затем compositor с простым оконным сценарием; после — GPU backend через изолированный интерфейс. Не привязывать весь compositor к одному конкретному драйверу.

### Slice 5 — пакеты и sandbox
Локальный пакет с манифестом, проверкой digest/подписи, атомарной установкой, откатом и приложением с ограниченными capabilities.

## Критерии готовности каждого компонента

- спецификация интерфейса и версия;
- положительный тест рабочего сценария;
- негативный тест отказа и проверки границ;
- диагностическое сообщение;
- измеримый критерий производительности или ресурсоёмкости, если это важно;
- инструкция сборки и воспроизведения;
- честная отметка статуса: planned, prototype, implemented, verified.

## Управление масштабом

В каждый milestone выбирается один главный вертикальный сценарий и небольшой список обязательных функций. Остальные идеи остаются в backlog. Количество подсистем, названий и каталогов не считается прогрессом без исполняемого результата.

**Итоговая формула DAKOS:** загрузиться воспроизводимо → изолировать процессы → определить стабильный ABI → подключить службы → вывести графику → управлять пакетами безопасно.
